# Automatic training and checkpoint selection

Each fresh run uses the installed base model, the selected dataset, and checkpoints created by that run. It does not need an earlier adapter, training report, reference recording, or user preset. A fresh run name cannot overwrite or append to an existing training history. Explicit **Continue run** and **Weights only** remain available when resuming is intended.

## Browser workflow

1. Prepare the user's recordings. **Prefer sidecar** uses matching SRT subtitles when available; sentence alignment checks their timing against the audio. Missing sidecars can use ASR. Inspect preparation warnings and clip boundaries.
2. Optionally run **Voice and transcript audit** with a clean reference of the intended speaker. Reserve complete source recordings for validation and, when enough material is available, a separate final test. The audit creates new datasets and preserves the prepared originals.
3. Cache the training dataset's features. Select it in **LoRA / DoRA Training**, choose a new name, and leave **Resume from** set to **Start fresh**.
4. Keep validation and automatic speech comparison enabled. Optionally enter the independently reserved dataset under **Final-test dataset**. This speech test reads audio directly and does not require a feature cache.
5. Start training. The dashboard reports optimization, checkpoint evaluation, and generated-speech comparison as separate phases. After evaluation, **Use best checkpoint** follows the speech recommendation, including Base when appropriate.
6. Open `analysis/speech_evaluation/listening_review.html` inside the training folder for a blind listening comparison. Select a prompt and seed, play the candidate clips, and optionally download your ratings. Ratings are not filled in by the model or silently used to change a checkpoint.

## How training stops

**Train speaker/extra modules in FP32** is enabled by default. It keeps the selected fully trained speaker projection, emotion layers, and mel embedding/head parameters and optimizer moments in FP32 so small learning updates are not rounded away. The frozen base keeps its configured precision and forward computation still uses the selected mixed precision. Turn the option off to store those modules in base precision and reduce memory use; CPU training still uses FP32. LoRA / DoRA parameters already use FP32 independently of this option. The choice is saved with presets and training runs, and applies before restoring weights and optimizer state when resuming.

The epoch/update budget is a maximum, not a target quality score. By default, validation runs every 250 optimizer updates and at epoch boundaries. Every absolute improvement may replace the separately saved best checkpoint.

Patience requires six checks without a loss improvement greater than 0.005. It begins after warmup, 1,000 updates, and two dataset passes. **Minimum updates between patience checks** defaults to the validation interval: nearby epoch-end checks can save a better checkpoint without consuming extra patience.

When patience first runs out and enough budget remains, the optional refinement trial multiplies the current and remaining learning-rate schedule by 0.5. It gives the lower rate 1,000 grace updates before patience resumes. The original maximum budget remains in force. The best score, patience spacing, refinement count, grace period, optimizer, and scheduler are saved for continuation. The trial is an experiment within a run; it is not guaranteed to improve every dataset.

Validation audio-token loss and auxiliary text-token loss are recorded separately and shown in the live status. Audio-token accuracy measures exact next-code prediction, not the percentage of correctly spoken words. A validation regression is a warning, not proof of memorization.

## Epoch probe and the two-signal stop

Token loss does not say how a checkpoint sounds, and on real voices the lowest-loss epoch and the best-sounding epoch are not always the same one. With **Probe each checkpoint with the deployment settings** enabled (the default), the run freezes `analysis/probe/plan.json` before training: three held-out sentences per held-out recording (at least 6, at most 12, or **Probe sentences**), balanced across recordings, with the run's recommended reference and two deterministic seeds per sentence (**Probe seeds per sentence**). Probe duration depends on the selected models, hardware, and prompt count; the automatic interval adjusts to its measured cost. After an epoch the trainer writes a temporary copy of the adapter and starts `indextts.training.probe_worker` in its own process. The worker renders the probe sentences with the settings Voice Generation applies by default for this adapter (the GPU tier's beams and diffusion steps, Smart sentences at the dataset profile's token target, the dataset's sentence and maximum pauses, the expressive clip as the emotion prompt), renders Base the same way once and caches that measurement, measures every clip against the real recordings (word error with the dataset's spellings forgiven, speaker and style similarity, pauses), and scores the epoch with the deployment score used by the final selection. The result is `analysis/probe/epoch_NNN.json`; `analysis/probe/summary.json` and the dashboard keep the per-epoch table.

Memory: the probe follows the epoch sample's rules, decided in the trainer before any worker starts. Beside the training model it runs only when the free memory covers **Minimum free VRAM** and the smallest generation tier's budget (5 GB), fits its memory tier to that free memory, releases the generation engine before the measurement models load, and with **Probe device** `auto` prefers another CUDA device with room when the machine has one. The training process never loads a generation or measurement model, so its own VRAM use does not change. **Probe every N epochs** 0 measures how long a probe takes (without the one-time Base render of the first probe) and spaces probes so they cost at most a third of the training time (a small, fast dataset may be probed every few epochs); 1 probes every epoch regardless; a failed, skipped or timed-out probe never fails training.

The best-scoring epoch is copied to `best/<name>_probe_best.safetensors`, shown as **probe-best** in checkpoint lists, evaluated by the teacher-forced pass and always included in the speech comparison, where it is judged like every other candidate. Two independent best checkpoints therefore survive a run: the lowest-loss update and the highest-scoring probe update.

Stopping uses both signals when **Let the probe confirm or defer early stopping** is on (the default). A validation-loss stall (the patience rules above) stops training only when the probe's deployment score has also failed to improve by more than **Probe minimum improvement** for **Probe patience** consecutive checks; while the probe still improves, the log records that training continues, and the optional lower-rate trial still runs when the loss first stalls. Separately, a probe whose word error is above the best check's by more than the tolerance (**Probe word-error tolerance**, or the recognizer's own error on the real probe recordings, at least one point) for the patience count, while its score has also stalled, stops training as overfitting even if the loss is still falling slowly. A probe stall alone never stops a run whose loss still improves, because the probe-best checkpoint is already saved. Without probe results (disabled, skipped, or not yet run) the loss decides as before. The probe state is saved with the training state, so a continued run keeps its best epoch, stall count and probe interval.

## How generated speech affects selection

All automatic reference choices share a **15-second target**: the saved adapter reference, epoch sample reference, training speaker/emotion conditioning, and validation/checkpoint evaluation. Selection preserves transcript-quality and boundary priorities, then chooses the nearest available duration within that speaker's training split. Other-reference modes exclude the current target clip; equally suitable alternatives can vary deterministically by seed and epoch. Known durations take precedence over missing duration metadata. Explicit self-reference modes and manually supplied sample references keep their requested behavior; training target utterances are not shortened or filtered to 15 seconds.

Before optimization, the run freezes `analysis/speech_evaluation/plan.json`:

- Six validation texts per held-out recording, at least 12 and at most 24 (or the configured **Held-out speech prompts**), balanced across source recordings, speakers, languages, and clip lengths; a longer concatenated prompt is added for each voice with enough texts. Six per recording keeps one recording's hard sentences from deciding the comparison and gives the paired bootstrap enough prompt clusters to resolve differences of a point or two of word error.
- A reference selected from that voice's actual training split and copied into the run. Selection prioritizes transcript agreement and matching boundaries, then duration near 15 seconds. The target and selected clip duration are recorded in new plans. Existing frozen plans retain their original references. Validation targets never supply their own voice references.
- Three deterministic generation seeds per prompt, plus the comparison margins. Audio hashes detect changed reference and target files.

After training releases its model, teacher-forced evaluation measures the saved checkpoints and Base. Speech comparison shortlists up to three distinct training updates: candidates with the lowest measured losses and the latest saved update, plus the probe-best update and the averaged and EMA files when they exist. It generates Base again using the same prompts, references and seeds. It never loads a preferred adapter from a previous run.

With **Compare with the deployment settings** (the default) each candidate is rendered the way Voice Generation deploys it by default. Base uses the selected language's default token limit, no emotion prompt, no inserted pauses, and the model's natural pace. Every checkpoint of the run shares one deployment: the GPU tier's beams and diffusion steps, Smart sentences packed to the dataset profile's token target and limit, the dataset's sentence and maximum pauses, the expressive training clip as the emotion prompt, and the speaking rate calibrated so far. Base and the adapters therefore form two render batches with the same sentences, reference and seeds, and the report records each candidate's settings under `candidate_inference`; the voice decoder gate, the decoding sweep and the final test render the selected checkpoint again with exactly those settings. The earlier behavior, every candidate at the fixed short-sample settings (3 beams, 25 diffusion steps, budget splitting, no emotion prompt), is still available by turning the option off.

Whisper transcribes the complete generated audio and matched real recordings. English, Spanish, and Arabic use word errors; Chinese and Japanese use character errors. Speaker and style embeddings sample up to three distributed 20-second windows. Reports include means, worst clips, possible truncation/repetition, invalid audio, transcript-edge disagreements, matched-text duration ratios, and the internal pause time of each generated sentence relative to the person's recording of it (silences of at least 120 ms between words and sentences; 1.0 matches the person, above 1 pauses longer, below 1 rushes). The pause ratio contributes to the deployment score described below. ASR errors on real recordings show that the recognizer itself is imperfect.

The selection policy rejects a candidate with an observed mean transcript-error increase over Base greater than 0.02, a mean speaker-similarity drop greater than 0.03, or more invalid/possibly truncated/repetitive clips. With the default **interval** guard the two margins disqualify only when the benchmark can resolve the regression: the paired prompt-bootstrap 95% interval must exclude zero, or a majority of the held-out recordings must show the regression (per-recording mean paired differences). A margin crossed by a few sentences of one recording while the other recordings improved is reported as a note, and the increase still costs deployment score (four times the mean word-error increase), so such a candidate wins only when its identity gain outweighs the doubt. The **mean** guard restores the earlier hard threshold. Frozen plans record the guard mode they were created with; plans from earlier versions keep the mean guard. Among the remaining candidates, one deployment score decides, the same score the voice decoder gate uses: the paired speaker-similarity gain over Base, minus four times any paired mean transcript-error increase (a point of error costs 0.04 of similarity), plus a pause term of 0.05 times how much closer to 1.0 the candidate's pause-time ratio is than Base's in log terms. Candidates within 0.002 of the best score are tied and the lower validation loss decides. Base scores 0 by definition and can win, which happens when every adapter gains identity but costs more word error than the gain is worth. The report lists every candidate's score and its three parts. The paired comparisons use 2,000 bootstrap draws over whole prompts, keeping a prompt's generation seeds together instead of treating them as independent observations, and their intervals are reported alongside the score.

The margins are configurable screening choices. These intervals describe the sampled prompts and do not establish performance on other speakers or recording sessions. Few validation sources, overlapping training/validation recordings, and unevaluated speakers are reported. Style, pace, edge checks, ASR, and embedding similarities are proxies; naturalness still requires listening. The result is a provisional automatic recommendation, not a guarantee of the universally best checkpoint.

## Speaking rate

Training first saves a pace estimate from the epoch samples. That compares one short sample sentence with the whole dataset's words per second, and long multi-sentence recordings speak faster per word than a single sentence, so the estimate tends to overstate how slow the adapter is. When the speech comparison completes with an adapter recommendation, the trainer recalibrates from the matched held-out sentences: the same texts spoken by the person and by the selected checkpoint, edge-trimmed, at least four clips. The earlier estimate stays beside it as `analysis/speaking_rate_training_samples.json`. Voice Generation shows the stored value in **Saved speaking rate for this LoRA / DoRA**; edit it and press **Save speaking rate** to override any estimate for that adapter. The stored method label tells you whether a value came from training samples, matched sentences, a grid, or a manual edit.

## Reference clips near the speaker's median

Automatic references balance recording quality, duration, pitch, and pace. With **Prefer a reference near the speaker's median pitch and pace** enabled (the default), the 24 best-quality candidates are measured (median voiced pitch with pyin, words per second from the transcript, cached in the dataset's `analysis/pitch_cache.json`) against the speaker's medians (pitch over a fixed sample of 48 clips, pace over every clip), and the nearest one wins; ten percent of pitch counts as much as fifteen percent of pace. The training log and the speech plan record the choice. Turning the option off restores the old rule.

## Decoding sweep

With **Sweep decoding settings after training** enabled (the default), the run ends by rendering the speech benchmark with the recommended checkpoint at other decoding settings, one change at a time: temperature 0.6 and 1.0 against the default 0.8, guidance rate 0.5 and 1.0 against 0.7, and 1 or 5 beams against 3. Each render is compared pairwise with the checkpoint's deployed measurement (same sentences, reference, seeds, and decoder adapter at its recommended strength) and scored as the speaker-similarity gain minus four times the word-error increase. A change is kept only when it scores at least 0.005 better and stays within the benchmark's regression policy; the winning changes are combined and checked once more, and the best passing candidate is saved as `analysis/decoding.json` (details in `analysis/speech_evaluation/decoding_sweep/report.md`). Voice Generation applies those settings together with the calibrated speaking rate when the LoRA / DoRA is selected, and `tools/sweep_decoding.py` runs the sweep for an existing training folder.

## Voice decoder adaptation

Generation has three stages: the GPT turns text into semantic tokens and decides what is said and when; the semantic-to-mel decoder (the s2mel flow-matching DiT) turns those tokens into a mel spectrogram and owns timbre and spectral detail; the vocoder renders audio. A LoRA / DoRA on the GPT cannot change how the decoder renders a voice, which it otherwise knows only through the reference clip of each generation.

With **Adapt the voice decoder after training** enabled (the default), a run trains a second, small adapter on the decoder's transformer blocks after checkpoint selection and the speech comparison. It uses the pretrained flow-matching objective on the cached dataset: each training clip is the target, a randomly drawn other clip of the same speaker (3 to 15 seconds, a new draw every epoch) is the in-context prompt, and the prompt's CAMPPlus style vector conditions the decoder, exactly as inference conditions it. Varying the prompt helps the adapter learn how to condition on different reference clips instead of relying on a single fixed reference.

The default is a DoRA of rank 128 and alpha 128 on all 65 attention and feed-forward projections at learning rate 2e-4. Every 500 updates and at every epoch boundary the trainer measures two things on held-out clips of the speaker (a dataset with too few recordings for a source split holds out clips instead): the flow-matching loss with repeatable noise, and **speaker identity**, the CAMPPlus similarity between eight clips re-rendered from their own semantic codes (a random training clip as the prompt, 16 solver steps, the app's guidance) and the real recordings. Identity selects the checkpoint; the loss guards it, because a checkpoint whose loss is above the pretrained decoder's is drifting from the decoder's own objective and is not kept. The stopping rules are the GPT trainer's: patience starts after 1,000 updates and two passes, the first exhausted patience halves the learning rate once with a grace period, the second stops the run. A GPU that runs out of memory on a long pair skips it and lowers the frame limit instead of failing.

An adapter is installed only when it measures better than the pretrained decoder twice. First, its re-rendered identity must beat the pretrained decoder's by 0.005. Second, when the run has a speech benchmark, the selected checkpoint renders the benchmark sentences again through the full pipeline with the adapter at strengths 1.0 and 0.6, and each render is compared pairwise (same sentences, reference, and seeds) with the checkpoint's earlier measurement without it: speaker similarity to the real recordings must rise by at least 0.005 and the word error rate may not rise by more than the benchmark's policy allows. Among the strengths that pass, the one with the best score (similarity gain minus four times the word-error increase) becomes the adapter's recommended strength, which Voice Generation applies whenever that LoRA / DoRA is selected; a lower strength often keeps most of the identity gain at a fraction of the intelligibility cost. Re-rendering recordings from their own codes cannot show what generated codes do to an adapter, which is why the full-pipeline test decides. A rejected file is parked under `analysis/quarantined_decoders/`, the training summary says why, and generation keeps the pretrained decoder. The accepted adapter is saved as `<name>.s2mel.safetensors` in the training folder, shared by every checkpoint of that training, and reported in `analysis/decoder_adapter.json` and `analysis/speech_evaluation/decoder_test/report.md`. The gate's word-error check follows the benchmark's guard mode: with the interval guard, an increase beyond the margin rejects a strength only when its interval excludes zero or a majority of recordings show it.

When the speech comparison preferred Base, earlier versions quarantined the decoder without a test, because the gate needs an adapter to render with. With **Judge the decoder with the best adapter even when Base leads** (the default) the decoder is judged with the best-scoring adapter checkpoint instead (the eligible adapter with the highest deployment score, otherwise the highest-scoring one), and the accepted combination is then judged as a whole deployment: Base, every measured GPT checkpoint and that checkpoint with its decoder at the accepted strength go through the same Base guards and deployment score (the gate's clips pair with Base's cells exactly like the GPT candidates' do, since they share sentences, reference and seeds). The result is appended to the speech report as the **joint deployment choice**; when adapter + decoder wins, it becomes the recommendation, the speaking rate is recalibrated from that checkpoint's matched sentences, and the decoding sweep and final test follow it. A decoder that improves its adapter but still loses to Base is installed for that adapter (Voice Generation loads it when the adapter is selected) while the recommendation stays Base. The measured cells and candidates of the development report are never changed by this step, so the gate, sweep and final-test provenance keep matching the report.

Voice Generation applies the decoder adapter automatically whenever a checkpoint of that training is selected: the **Voice decoder adapter** dropdown returns to the adapter saved with the LoRA / DoRA each time one is selected, **None** plays the GPT adapter alone, any other decoder adapter file can be chosen, and **Voice decoder adapter strength** scales it independently of the LoRA / DoRA strength. With classifier-free guidance the adapter renders the conditioned branch while the unconditional branch keeps the pretrained decoder, so guidance steers toward the adapted voice instead of subtracting it. `tools/train_decoder_adapter.py` adds a decoder adapter to an existing training folder without retraining the GPT adapter and runs the same full-pipeline test when the folder has a speech benchmark (`--no-test` skips it, `--checkpoint` picks the GPT checkpoint to test with). The decoder adapter is trained from the dataset rather than from a particular GPT checkpoint, so it does not depend on which checkpoint is selected.

## Independent final test

An optional final-test dataset must use separate source recordings. The app rejects overlapping source names, shared audio paths, and byte-identical copies of training/validation files. Curated test datasets may include training-reference rows; only their `split=val` rows become test targets.

The final-test plan is frozen before training. After development selection, `final_test/selection_frozen.json` records the decision. Only that selected model and Base are generated on the final test. Results report whether the frozen selection passes the observed regression guards; they do not choose another checkpoint after looking at the test set. Repeated tuning against this test would turn it into development data.

## Results and recovery

The training folder retains the loss-best checkpoint (`best/<name>_best.safetensors`) and the probe-best checkpoint (`best/<name>_probe_best.safetensors`) separately from the final file; `analysis/probe/` holds the probe plan, the Base cache, every epoch's measurement and the summary table. `analysis/checkpoint_eval.json` stores measured token losses.

`tools/rerun_selection.py --adapter-dir loras/<name> --fresh-plan --restore-decoder --defaults` applies the current selection system to an existing training folder without retraining: it rebuilds the benchmark plan with the current settings (the previous `analysis/speech_evaluation` folder is kept beside it with a timestamp), runs the speech comparison, judges the installed or newest quarantined voice decoder adapter with the joint deployment choice, then runs the decoding sweep and the final test. Every phase is the trainer's own child process and uses the same local models; no network access is needed. `analysis/speech_evaluation/report.json` and `report.md` store the speech recommendation, per-clip results, settings, hashes, uncertainty, and coverage warnings. `grids/` contains the actual comparison WAV files; `final_test/` contains independent confirmation when configured.

Evaluation runs in a bounded child process after training frees its model. Cancellation, timeouts, missing resources, and evaluation failures are shown in the dashboard and log; they do not invalidate the saved training weights. A failed speech comparison leaves the loss-based fallback visible instead of claiming that audio quality passed. A missing recommended file produces an error rather than silently selecting the final checkpoint.

Whisper is downloaded through the existing model downloader if absent. The normal installed speech models provide the speaker/style measurements. The feature adds no dependency on a particular computer path or past training. Real GPU/UI verification is still needed on each supported hardware configuration; unit tests alone do not establish memory fit or audio quality.
